## 做法

| 層 | 位置 |
|---|---|
| 純邏輯（不依賴 Phaser、DOM） | `lib/games/mine-descent/`（config、course、sim、session、autopilot、share-code、records、account-records、leaderboard、sync-state、sound-mix、meta、share/card） |
| 場景與美術（Phaser 4） | `app/games/mine-descent/`（art.ts 程式產生的 SVG、scene.ts、sound.ts） |
| 畫面 | `app/components/mine-descent/`（介紹頁、遊戲畫面、各面板） |
| 伺服器 | `server/api/games/mine-descent/`、`server/utils/mine-descent-records.ts`、migration `0006` |
| 文字 | `lib/i18n/dictionaries/*.ts` 的 `mineDescent`（七種語言） |

玩法：無盡模式。每局隨機岩板（保證每層有一條走得通的路），體力 6 格，頂端崩塌線隨深度往下壓。計分＝深度分＋驚險分＋水晶分，連續驚險有倍率。排行榜兩張：最深、最高分。

## 同步檢查表（docs/dev/sync-checklist.md 第 1、2、7 節）

沿用下班逃離辦公室的做法（兩款的同步程式結構相同）：伺服器只存最佳紀錄、取高值，重送一定是冪等的，不需要批次代碼。差別只有紀錄的內容：`mode` 是 `score`（最高分）或 `depth`（最深公尺），沒有日期，所以沒有過期與跨午夜的問題（sync-checklist 第 5 節不適用）；本機驗證時間的上限仍是手機時鐘快 1 天。

## 同步檢查表（docs/dev/sync-checklist.md 第 1、2、7 節）

先決定：**伺服器只存「取高值」的最佳紀錄，沒有累計次數，所以重送一定是冪等的**。這讓精準停車最複雜的部分（outbox、syncId、不明確結果、dropForeignOutbox）全部不需要。唯一需要穩定代碼的是「建立訪客」（找回同一個訪客，T9），代碼放在 pending 狀態裡。

### 第 1 節：共用狀態與寫入者

| 狀態 | 存在哪裡 | 誰會寫 | 怎麼避免同時寫 |
|---|---|---|---|
| 本機最佳紀錄（顯示用快取） | `game-station:mine-descent:v1`（localStorage） | 玩完一局（`recordRun`）、同步回應（`replaceRecords`）、登出清空 | 只當顯示快取；真正的資料是「伺服器＋pending＋inbox」。玩完一局的寫入是取高值，同步回應整份換成「帳號紀錄與 pending 取高值」 |
| 待上傳（pending） | `game-station:mine-descent:pending:v1` | 只在同步的 Web Lock 裡：收 inbox、送出成功後移除已確認的項目、登出清空 | 第 1 種：鎖裡讀→改→寫。內容：`{ guestSyncId, bests: [{mode, score, achievedAt}] }`，mode 是 score 或 depth，同一種只留最高值 |
| inbox | `game-station:mine-descent:run:<隨機代碼>` | 玩完一局時新增一個新的 key（不改共用 key） | 第 2 種：只新增、不改；由鎖裡的同步收走並刪除（先寫成功 pending 才刪 inbox） |
| 登出記號 | `game-station:account:signed-out` | 沿用精準停車（登出、刪除帳號、刪除訪客時寫） | 其他分頁收到就當作已登出，並用同一個 epoch 機制作廢送出中的請求 |
| 伺服器 `mine_descent_bests` | D1 | `POST /records/sync` | `UPDATE … WHERE score < ?` 條件更新；沒有就 INSERT，撞到唯一鍵（P2002）重試條件更新 |
| 訪客與 cookie `gs_guest` | D1、cookie | 沿用平台（建立訪客、合併、刪除） | 沿用平台機制；`mergeGuest` 加上 mine_descent_bests 的合併 |

不支援 Web Locks：退回「不鎖」，因為所有寫入都是冪等的取高值，兩個分頁各送一次不會出錯；pending 的移除只移除「分數不高於這次送出的」，所以多送不會丟資料。

### 第 2 節：每個請求的結果

| 結果 | 處理 |
|---|---|
| 沒有回應（離線、逾時） | pending 原封不動；`online`、下一局結束、打開介紹頁或 /me 時重送 |
| 伺服器已寫入但回應沒收到 | 重送同樣的 bests：取高值冪等，不會重複；建立訪客用同一個 `guestSyncId` 找回同一個訪客並補發 cookie |
| 400 | 整批格式或分數範圍不對（正常前端不會送出）：丟掉這一批的 bests，不再重送壞資料 |
| 401 | Google：當作登出（`expireSession`），本機與 pending 留著，下次登入時併進帳號；訪客 cookie 無效：當作沒有身分（`expireGuest`），pending 留著，下一局再建立新訪客 |
| 403 consent_required | 歐盟地區還沒同意：pending 留著，顯示結算的上榜詢問 |
| 403 其他、413、429、5xx、格式不對 | 當作暫時失敗，pending 留著，下次重送 |
| 409 account_mismatch | 另一個分頁換了身分：epoch +1、重新讀登入狀態；pending 留著，送給新的身分 |
| 晚到的回應，期間已登出或換帳號 | epoch 或登出記號變了就整個丟掉，不寫回本機 |
| 晚到的回應，期間本機有更新 | 回應套用時取「帳號紀錄、pending、本機」三者的高分，不蓋掉新的 |
| 送到一半頁面關掉 | pending 在 localStorage，新頁面接手重送（冪等） |
| 送出後頁面關掉、沒有任何回應 | 同上；不需要「不明確」狀態，因為重送不會重複 |

### 第 7 節：登入狀態的結束方式

| 情況 | 本機資料 | 這一頁登入狀態 | 其他分頁 |
|---|---|---|---|
| 這一頁按登出 | 清本機最佳、pending、inbox（第 16 題）；最後才發布新的身分狀態 | 已登出 | 收到登出記號，epoch +1、清空、重新讀取 |
| 刪除帳號 | 同上；伺服器 CASCADE 刪 mine_descent_bests | 已登出 | 同上 |
| 401（過期） | 留著（下次登入併進帳號） | `expireSession` | 各自收到 401 時處理 |
| 另一個分頁登出後可能登入別的帳號 | 已被那個分頁清掉 | 收到記號後重新讀取 | — |
| 過期後另一個分頁直接登入別的帳號 | 留著，送給目前 cookie 的帳號 | 這一頁以為的 playerId 與 cookie 不同，伺服器回 409，重新讀取 | — |
| 刪除訪客紀錄 | 同登出：先清本機、最後才變成沒有身分 | 沒有身分 | 同登出 |

## 偏離清單（和設計稿不同的地方）

| 項目 | 設計稿 | 實作 | 原因 |
|---|---|---|---|

**還沒處理（和下班逃離辦公室、精準停車共用的程式，修了會動到另外兩款，等使用者決定）**：

- 第 1 項：帳號切換後，舊帳號還沒送完的成績會轉送給新帳號。
- 第 2 項：同步 POST 在確認身分之前就可能合併並刪除訪客。
- 第 3 項：紀錄與名次兩支 GET 會順便延長或刪除 session（`server/utils/guest.ts`、`lib/account/session.ts`）。
- 第 4 項：沒有 Web Locks 時兩個分頁可能互相覆蓋 pending。
- 第 5 項：一筆壞資料讓整批被拒、時鐘偏差讓沒寫入的紀錄被當成成功。
- 第 7 項：同值的創下時間取決於哪台裝置先同步。
