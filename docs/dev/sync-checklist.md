# 同步與共用狀態的改動標準

只要改動碰到下面任何一項，就照這份標準做：

- 瀏覽器裡多個分頁共用的資料（localStorage、IndexedDB、cookie）
- 會改資料庫的 API
- 「先存本機、之後再送」的流程（佇列、重送、合併）
- 登入、登出、刪除帳號、登入過期

為什麼有這份標準：精準停車的紀錄同步（2026-11-21）前後被 Codex 審查了五輪，每輪都找到新問題，例如重複加次數、整批被拒時丟資料、分頁之間互相觸發、跨過午夜被拒。這些問題都能在寫程式前列表想清楚。規則是：**先把下面每一節的表填完再寫程式；審查找到新的一類問題，就補進這份文件。**

## 1. 列出所有共用狀態和寫入者

每一份共用狀態都列一行：

| 狀態 | 存在哪裡 | 誰會寫（哪個函式、哪個分頁、哪個請求） | 怎麼避免同時寫 |
|---|---|---|---|

規則：

- **每一份狀態只能用下面其中一種方式寫**，不能混用：
  1. **只在鎖裡做「讀→改→寫」**：瀏覽器分頁之間用 Web Locks（`navigator.locks.request`），伺服器用條件更新、`ON CONFLICT`、觸發器。
  2. **只新增、不改**：每次寫一個新的、名稱不重複的 key（例如 `prefix:<隨機代碼>`），由持有鎖的那一方收走並刪除。
- 不在鎖裡的程式（例如玩完一局的當下）不能讀改寫共用 key，只能用第 2 種。
- 「只是順便寫回」也算寫入：例如讀取時把過期資料清掉再存回，同樣要在鎖裡。
- **「收走」一定要先寫成功才刪來源**：把 A 併進 B 時，B 寫入失敗就不能刪 A，而且這一輪要中止，不能拿只在記憶體裡的 B 繼續送。不然下一輪又會從 A 收到同一份、用新的批次代碼再送一次。
- **顯示用的快取不能當作判斷依據**：例如「本機紀錄比較高，所以這局不用上傳」。快取可能是別的帳號或過期的資料；要上傳的東西照實記下，讓伺服器取高分決定。
- 鎖不存在時的退路要寫清楚（例如不支援 Web Locks 的瀏覽器）。

## 2. 每個請求的結果表

每個會送出的請求，下面每一種結果都要有明確的處理，寫進程式註解和測試：

| 結果 | 要回答的問題 |
|---|---|
| 沒有回應（離線、逾時） | 資料留在哪裡？下次什麼時候重送？ |
| 伺服器已經寫入，但回應沒收到 | 重送時伺服器會不會重複寫？（見第 3 節） |
| 400（伺服器說資料不合理） | 合理的那部分會不會跟著丟掉？會不會一直重送同一份壞資料？ |
| 401（登入過期） | 本機資料要不要留？登入狀態要不要改？ |
| 403、413、429、5xx、回應格式不對 | 當作暫時失敗，下次重送；不能當作成功 |
| 回應晚到，這段期間已經登出、換帳號 | 回應要丟掉，不能寫回本機 |
| 回應晚到，這段期間本機有更新的資料 | 套用回應時不能蓋掉那些更新 |
| 送到一半頁面關掉或重新整理 | 新頁面能不能馬上接手重送？ |

## 3. 會「增加」的寫入一定要能擋重複

- 計數、累加這類寫入（例如完美次數 +3），一定要帶前端產生的批次代碼。伺服器**記下代碼和累加要在同一個資料庫動作裡完成**（觸發器、同一個 SQL）。不能先記代碼再加，也不能只記「最後一個代碼」。
- 「取高分」「覆蓋成某個值」這類重複套用不會變的寫入，可以不帶代碼，但要用條件更新（`WHERE score < ?`），而且要處理兩個請求同時建立同一筆的情況（撞到唯一鍵時重試）。
- 擋重複用的紀錄要**保留得跟前端可能重送的時間一樣久**。前端沒有期限，伺服器就不能清。

## 4. 並行的三種來源都要想過

1. 同一個瀏覽器的多個分頁：共用 localStorage，各自有記憶體和計時器。
2. 同一個帳號的多台裝置：只在伺服器上相遇。
3. 同一個人同時送出的多個請求（重送、兩個分頁、快速連按）。

每種都問：兩邊同時讀到舊資料、各自寫回，會不會少一筆或多算一次？

## 5. 時間與日期

- 前端和伺服器判斷「有沒有過期」「是不是今天」要用**同一個函式**，放在共用的 `lib/`。
- 手機時鐘可能快、也可能慢：日期和時間的檢查要容許誤差。收下的資料，讀取時也要讀得回來（上限一致）。
- 跨過午夜、跨過保存期限的那一刻要想清楚：**過期的資料不是錯誤資料**，略過就好，不能讓它讓整批被拒絕。
- 前端送出前先依同樣的規則濾掉、拆批，不要依賴伺服器拒絕。

## 6. 觸發與重送

- 列出所有會觸發同步的事件（登入、玩完一局、網路恢復、打開某些頁面）。
- **同步過程自己的寫入不能當作觸發來源**，否則分頁之間會互相叫醒、無限重送。只聽「真的有新資料」的事件。
- 每次觸發的重試次數有上限；失敗後不自動重試，除非失敗期間又有新的觸發（例如網路剛恢復）。
- 同步正在跑時收到的觸發不能被吞掉：記下來，跑完補一輪。

## 7. 登入狀態的各種結束方式

逐一寫出要清什麼、留什麼：

| 情況 | 本機資料 | 這一頁的登入狀態 | 其他分頁 |
|---|---|---|---|
| 這一頁按登出 | | | |
| 刪除帳號 | | | |
| 伺服器回 401（過期） | | | |
| 另一個分頁登出，之後可能登入別的帳號 | | | |
| 登入過期後，另一個分頁直接登入別的帳號（沒有按登出，cookie 被換掉） | | | |

規則：

- 其他分頁登出時，這一頁要立刻當作已登出並重新讀取登入狀態，不能繼續用舊帳號的身分送資料。登出前送出的請求，回應一律丟掉（每一頁自己的計數，再加上分頁共用的記號）。
- **cookie 可能在這一頁不知道的情況下換成別的帳號**（最後一列）。所以會寫入帳號的請求要附上「這一頁以為的帳號 ID」，伺服器確認跟 cookie 是同一人才寫入，不同就回 409，前端重新讀取登入狀態。讀取的請求也一樣，不然會把別人的資料顯示在舊帳號的畫面上。
- 送出過、還沒收到回應的批次要記住是送給哪個帳號；換了帳號就不能再送給新帳號（舊帳號可能已經收到了）。

## 8. 退路

- 瀏覽器不允許儲存（無痕模式）：改記在記憶體，功能照常。
- 寫入失敗（空間滿了）：之後以記憶體那份為準，不能讀回比較舊的那份。
- 不支援 Web Locks：退回有期限的鎖定標記，並寫明會有什麼限制。

## 9. 流程

1. 寫程式前，把第 1、2、7 節的表填在設計稿或 PR 說明裡。
2. 每一列至少對應一個測試：能用單元測試的用單元測試（純邏輯放 `lib/`），跨分頁、網路失敗用 E2E（Playwright 的 `context.route` 擋請求、`context.newPage()` 開第二個分頁）。
3. 寫完先自己照這份文件逐節檢查一次，再請 Codex 審查。
4. 審查找到的問題，如果這份文件沒涵蓋，就先補進文件再修。
