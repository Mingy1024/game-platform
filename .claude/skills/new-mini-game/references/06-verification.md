# 階段 7：驗證與驗收

實作完成不等於完成。精準停車在這個階段找到並修好 15 個問題，其中「過站後畫面變黑」這種嚴重問題，只靠單元測試和型別檢查完全看不出來。

## 順序

1. **逐張看截圖**（最容易漏，也最有價值）
2. **寫 E2E 測試**
3. **品質關卡**：型別、lint、單元、E2E、build
4. **逐條驗收**，不符的修正後重跑受影響條目
5. **交驗收報告**

## 1. 截圖檢查

用開發掛勾（自動駕駛＋加速）跑完整局，在每個階段截圖，然後**真的打開每一張看**。用 `scripts/sheet.cjs` 把同一畫面的多種語言並排，一次比對。

必看的組合：

- **畫面**：介紹頁（整頁）、關卡介紹、行駛中、放大時、判定（成功與失誤各一）、結算、分享面板、暫停
- **寬度**：手機 360、390；電腦 1280（N1 還要 1920 沒有橫向捲軸）
- **語言**：七種都要；字最長的越南文、葡文和音譯最長的韓文、英文最容易出問題
- **特殊狀態**：減少動態效果、開關打開的預留版位、瀏覽器不能儲存、圖片載入失敗

每張要看：按鈕有沒有被切掉、文字有沒有截斷或重疊、元素有沒有互相遮擋、數字格式（−0、千分位、小數點依語言）、和設計稿是否一致。

自動偵測溢出只能當輔助（`scrollWidth > clientWidth`），它抓不到「被父層裁掉」或「截斷加省略號」的情況；精準停車的音譯站名截斷就是靠肉眼看圖發現的。

## 2. E2E 測試

放在 `tests/e2e/`，playwright.config 有 desktop（1280×900）和 mobile（Pixel 7）兩個 project。測試名稱用驗收編號開頭（`"E2 E4 鍵盤：…"`），驗收時直接對照。共用的 helpers（進遊戲、出發、讀 snapshot、自動駕駛跑完整局、收集主控台錯誤）在 `tests/e2e/helpers.ts`。

標 E 的驗收條目都要有對應測試。常用手法：

- 觸控：對遊戲框 dispatch `PointerEvent`（pointerType touch），測多指與 pointercancel
- 切分頁：覆寫 `document.hidden` 再送 `visibilitychange`
- 不能儲存：addInitScript 讓 `Storage.prototype.setItem` 丟錯
- 系統分享：addInitScript 假造 `navigator.share`／`canShare`，記錄呼叫內容
- 載入失敗：`page.route` 擋掉某張圖
- 主控台：收集 error 與 warning，忽略無頭瀏覽器的「GL Driver Message」

## 3. 品質關卡

全部要過（驗收 Q1），指令見 05 的「執行環境」。另外量：

- **fps**：正式版 build 後用 rAF 間隔量，電腦一般速度、手機用 CDP `Emulation.setCPUThrottlingRate` 4 倍降速。開發版比較慢，要用正式版量才準。
- **首次載入**：遊戲進場的圖片總量、介紹頁不載入遊戲引擎（N5）。
- **Lighthouse**：需要下載工具，請使用者自己跑：`npx lighthouse http://localhost:3000/games/<slug> --form-factor=mobile`。

## 4. 逐條驗收

每一條實際檢查，把結果填進 `docs/acceptance/<slug>.md` 的結果欄，格式：

- `通過｜<證據>`（例：`通過｜單元 B1`、`通過｜E2E F5`、`通過｜截圖 7 語言`）
- `修正後通過：<原本的問題>｜<證據>`
- `通過（模擬）｜<證據>；實機…待確認`
- `部分通過：<哪部分過了>｜<證據>；<哪部分沒驗證、為什麼>`

並在文件開頭註明「最近一次驗收：<日期>」。發現清單本身和設計稿不一致（例如背景數量），先改清單並註明。

## 偏離清單

從實作開始就維護一份「和設計稿不同的地方」：項目｜設計稿｜實作｜原因。改任何設計稿寫明的數值或做法時當下記一筆，原因寫實話；不確定原因就寫不確定，不要事後編理由。驗收報告和開發紀錄都會用到這份清單。

## 5. 驗收報告

在對話中交，簡潔具體：

- 品質關卡結果（數字）
- 驗收統計：直接通過／修正後通過／部分通過／模擬通過各幾條
- 這輪找到並修好的問題（每個一行：症狀、原因、怎麼修）
- 需要使用者決定或執行的事（附可以直接執行的指令）
- 需要人工確認的項目（實機手感、分享選單、翻譯、美術）
- 偏離設計稿的地方

不要用「應該沒問題」之類的模糊說法；沒驗證的就說沒驗證。
