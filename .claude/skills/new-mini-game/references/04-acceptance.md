# 階段 5：驗收標準

使用者的要求：「實作前建立一套檢驗規則，實作完後依這套標準比對有無符合規格，有問題的部分整理列出並修正」。

範本就是 `docs/acceptance/precise-stop.md`（91 條）。新遊戲寫成 `docs/acceptance/<slug>.md`，結構照抄，內容依設計稿重寫。

## 檔案結構

1. 標題、設計稿網址、總條數。
2. **怎麼使用**：每條實際執行檢查、記錄結果（通過／不符／無法驗證＋證據）、不符的列出並修正、修完重跑受影響條目與品質關卡、交驗收報告。並寫明「規格變動時先改這份清單，再改程式」。
3. **檢查方式代號**：U 單元測試、E 自動操作測試、S 截圖比對、C 指令／檔案檢查、M 人工確認。
4. 分組表格：`| 編號 | 規則 | 檢查 | 結果 |`，結果欄先留空。
5. **需要你人工確認的項目**：實機手感、系統分享選單、翻譯品質、美術觀感等。

## 分組

| 組 | 內容 | 新遊戲怎麼寫 |
|---|---|---|
| A | 目錄與範圍 | 目錄資料、分類、封面、各列表頁看得到、沒做「這次不做」的項目 |
| B | 核心規則／物理 | 依設計稿重寫，每個數值一條 |
| C | 計分 | 依設計稿重寫：各區間、邊界值歸屬、時間規則、連擊、滿分、設計稿範例算得出來 |
| D | 關卡產生 | 依設計稿重寫：關數、各關範圍、每日種子可重現、隨機模式 |
| E | 操作 | 手機與電腦的每個操作、自動暫停、不捲動頁面、不跳出選字選單 |
| F | 畫面與流程 | 流程順序、每個畫面顯示的資訊、不顯示的資訊 |
| G | 動畫特效 | 每個特效一條，加上減少動態效果、粒子上限、特效不影響判定 |
| H | 美術資產 | 圖檔在專案內、WebP、各關背景、首次載入大小上限 |
| I | 介紹頁與整頁切換 | 大多可沿用精準停車的 I1–I9，換掉遊戲專屬的名詞 |
| J | 紀錄與分享 | 大多可沿用 J1–J7 |
| K | 多語系 | 大多可沿用 K1–K8；K6（360 px 與 1280 px 不截斷）一定要保留 |
| L | 開關與資料庫 | 開關沿用 flags；migration 只建這款的表 |
| P | 帳號紀錄同步 | 預設要有（沒規劃排行榜的遊戲才省略），可沿用礦坑大逃亡的 P 組，第一條是先照 docs/dev/sync-checklist.md 填表 |
| T | 全站排行 | 預設要有，可沿用礦坑大逃亡的 T 組，換成這款的榜與排序 |
| N | 體驗、無障礙、效能 | 可沿用 N1–N6；依遊戲調整 fps 目標 |
| Q | 品質關卡 | 可沿用 Q1–Q4 |

## 寫規則的要點

- 每條都要能驗證：寫數值、範圍、畫面上看得到的東西，不寫「手感良好」這種判斷（那些放人工確認）。
- 檢查方式選最便宜可靠的：數值規則用 U，流程用 E，畫面用 S。
- 數字要和設計稿完全一致。之後若改數值，先改清單和設計稿，再改程式，並記進偏離清單。

## 關卡

寫完給使用者看。使用者通常會要求先 commit（例：`docs: 新增<遊戲名>驗收標準`），然後說「開始實作」。
