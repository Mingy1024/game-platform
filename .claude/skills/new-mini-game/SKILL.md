# 遊戲小站：新小遊戲開發流程

這份流程來自第一款遊戲「精準停車」（2026-11-15～16）的實際開發。它的核心是**每個階段都等使用者確認才往下走**：使用者要的是可以掌控方向的協作，不是一次丟出成品。跳關會讓使用者失去決定權，後面也常要整段重做。

## 流程與關卡

| 階段 | 做什麼 | 關卡（停下來等使用者） | 細節 |
|---|---|---|---|
| 0. 接手 | 判斷目前在哪一階段 | — | 本檔「中途接手」 |
| 1. 選題 | 列 3–6 個題材建議 | 使用者選定題材 | references/01-ideation-research.md |
| 2. 研究 | 類似遊戲、玩法、計分、技術做法 | 研究摘要給使用者看過 | references/01-ideation-research.md |
| 3. 需求確認 | 一題一題問，每題附建議 | 每一題都要有使用者的決定 | references/02-requirements.md |
| 4. 設計稿 | Design canvas Artifact：畫面、情境、討論整理、規格 | 使用者明確說「確認」或「開始實作」 | references/03-design-artifact.md |
| 5. 驗收標準 | 依設計稿寫 docs/acceptance/<slug>.md | 使用者看過清單；通常會要求先 commit | references/04-acceptance.md |
| 6. 實作 | 純邏輯模組 → 遊戲畫面 → 介紹頁 → 分享 → 多語系 | 不停，直接接著做第 7 階段 | references/05-implementation.md |
| 7. 驗證與驗收 | 截圖檢查、E2E、品質關卡、逐條驗收並修正 | 全部做完才交驗收報告，列出偏離與待人工確認 | references/06-verification.md |
| 8. 交付 | commit／push（使用者要求時）、開發紀錄、跑伺服器給使用者看 | 使用者說了才 commit、push | references/07-delivery.md |

進入一個階段時，先讀那個階段的附檔。附檔寫了格式、檢查項目和上一款踩過的坑。

### 實作到驗收：一口氣做完

使用者說「開始實作」之後，第 6、7 階段連續做完，中間不回報進度、不停下來給使用者看半成品，最後一次交驗收報告。使用者要看的是驗收過的結果，不是一路的進度。

只有遇到**真正需要使用者決定的事**才停下來問：

- 設計稿沒寫清楚、或兩處互相矛盾，而且不同解讀會讓玩家感受到差別（玩法、計分、難度、畫面呈現）。
- 照設計稿做不到或明顯不好，必須偏離，而且這個偏離玩家感受得到（例如一局時長、判定範圍、拿掉某個畫面）。
- 影響範圍超出這款遊戲的決定：repo 會多出大量檔案（例如自行託管字型）、要改平台共用的元件或其他遊戲、要新增外部服務或套件。
- 被權限擋下的動作（例如用 npx 下載工具），而且不做就無法完成某條驗收。

問的時候把同一時間累積的問題合在一次 AskUserQuestion 裡，每題附建議，答完繼續做到底。

其他技術選擇自己決定，例如元件怎麼拆、玩家感受不到的數值微調、測試怎麼寫。凡是和設計稿寫法不同的，都記進偏離清單（附檔 06），在驗收報告裡一起交代。不要因為「想讓使用者知道」就中途停下來回報。

## 使用者固定的偏好（每一款都適用）

這些是使用者在第一款遊戲明確講過的，不必每次重問，但做法要照著來：

- **只做原創**：不重製既有遊戲的名稱、角色、美術、關卡或用語。參考別的網站時只取「方向」，版位和元件要自己設計，而且體驗要更好。
- **先確認再實作**：研究完一題一題問，設計稿確認後才寫程式。
- **有音效、沒有震動**（2026-11-16 改）：遊戲預設有音效，手機震動不做。音檔由使用者用本地模型生成：列出需要的音效、每個附英文提示詞和規格（長度、是否循環、格式），等使用者交檔再接進遊戲。
- **畫面與生圖交給 Codex**：`codex exec --skip-git-repo-check -s workspace-write -C <dir> --enable image_generation "<prompt>" < /dev/null`。一定要接 `< /dev/null`，否則會卡住等輸入；不要用 `pkill -f "codex exec"`，它會連自己的指令一起砍掉。
- **介面不放多餘說明文字**：例如分享面板不寫「會帶過去的內容」，語言選單不附中文註解。能用圖示、顏色、版面表達的就不要加一句話。
- **用驗收清單檢查**：實作完逐條比對，不符的列出並修正，再交報告。規格有變動時先改清單再改程式。
- **Git**：commit 直接在 main，不開分支；只有使用者要求時才 commit 或 push。commit 訊息結尾用系統提供的 attribution。
- **使用者的 email 是私人資訊**，不可以送到任何外部服務。
- **同步類改動先照檢查表**（2026-11-21）：紀錄同步、排行榜、任何「本機先存、之後送伺服器」或分頁共用資料的改動，寫程式前先照 `docs/dev/sync-checklist.md` 把共用狀態、請求結果、登入狀態的表列完，每一列對應測試，自己逐節檢查過才請 Codex 審查。精準停車的紀錄同步沒先做這件事，Codex 審了五輪、每輪都找到新問題，浪費使用者的 token。
- **稱呼與語氣**：用繁體中文、台灣用語；回報要具體（數字、檔名、條目編號），不要空泛的形容詞。

## 平台已經定案的預設（新遊戲沿用，需求確認時只需快速確認）

精準停車確立了平台的共同做法。新遊戲預設照做，在需求確認階段列成「沿用平台預設」一題讓使用者確認或排除，不要逐項重新討論：

- 首頁點遊戲 → 先進**介紹頁**（同一網址）；只有介紹頁的出發鈕會開始；按下後**整頁切換**成遊戲畫面，網址不變，返回鍵回介紹頁。
- 介紹頁：主視覺、開始區（各模式出發鈕＋我的最佳）、我的紀錄、怎麼玩、判定與計分、常見問題；**廣告只有一個版位**，在「怎麼玩」和「判定與計分」之間；遊戲畫面完全沒有廣告和網站選單。
- **預留版位**：全站排行（我的紀錄旁的分頁）、Google 登入、累計遊玩次數；由 `lib/flags.ts` 的開關控制，預設關閉，正式畫面不顯示假資料。
- **結算分享**：成績圖 1080×1350、成績專屬連結 `/games/<slug>/r/<代碼>`、手機用系統分享選單、電腦提供 LINE／Facebook／X／下載／複製連結。
- **七種語言**：zh-TW（預設、無前綴）、/zh-cn、/en、/ja、/ko、/vi、/pt（巴西葡文）。不依瀏覽器語言自動跳轉，記住使用者選過的語言。
- **紀錄存在本機**（localStorage），瀏覽器不允許儲存時照常能玩。
- **動畫特效**要有，並提供「減少動態效果」的簡化版。
- **音效、音樂與聲音鈕**（2026-11-20 改）：遊戲畫面右上、暫停鈕左邊放兩顆圖示鈕：音符只開關背景音樂、喇叭只開關音效，互不影響；暫停選單也有「音效」「音樂」兩個開關，和右上同步；預設都開；兩個選擇全站共用，記在本機。介紹頁不出聲、不載入音檔。
- **原創美術**：立體渲染的角色與場景由 Codex 生成；需要精準對位的元素（目標區、刻度、介面）用程式繪製。

## 中途接手

使用者可能從中間開始（「設計稿已經好了，開始實作」）。先判斷現在在哪一階段：

1. 讀專案記憶（MEMORY.md 指到的檔案），找這款遊戲的設計稿網址與進度。
2. 有設計稿 Artifact → 用 Artifact `read` 讀最新版，讀 `project/Main.dc.html` 的討論整理與規格。
3. 有 `docs/acceptance/<slug>.md` → 驗收標準已定；結果欄有沒有填，代表驗收做過沒有。
4. `git log` 和 `git status` 看實作做到哪裡。

判斷不出來就問使用者一句「目前要從哪一步開始」，附上你的判斷。

**前面的關卡沒過，就先補前面的**，即使使用者叫你做後面的。最常見的情況：使用者說「開始實作」，但 `docs/acceptance/<slug>.md` 還不存在。這時先依設計稿寫驗收清單給使用者看（階段 5），再開始寫程式。理由是使用者明確要求驗收標準要在實作前定好，事後才寫的清單只會照著程式寫，失去檢查的意義。補的時候跟使用者說一句為什麼先做這個。

## 什麼時候不用整套流程

已上線遊戲的小修改（修 bug、調整文字、改一個數值）不必從選題走起。照這三點就好：

- 改到設計稿或驗收清單寫明的規格時，先改清單（必要時也改設計稿）、記進偏離清單，再改程式。
- 修完跑相關的單元測試與 E2E，並重跑受影響的驗收條目，更新結果欄。
- 畫面有變動就截圖檢查，至少看手機 360 px 和最長的語言。

新增模式、新增關卡類型這種會改玩法的需求，回到階段 3：把要決定的事一題一題問。

## 長流程的節奏

一款遊戲的完整流程會超過一次對話的容量（精準停車壓縮過兩次）。為了接得上：

- 每完成一個階段，更新專案記憶裡這款遊戲的進度檔（設計稿網址、已完成、還沒做、環境注意事項）。
- 第 5 階段結束、使用者說「開始實作」之前，是壓縮對話的好時機，可以建議使用者先執行 `/compact`。實作和驗收期間不要停下來要求壓縮：對話會自動摘要，只要進度檔隨時更新就接得上。
- **偏離設計稿的地方當下就記下來**（附檔 06 的「偏離清單」）。精準停車有一項數值（目標時間 ×1.3 改成 ×1.2）實作時改了卻沒回報，到整理開發紀錄時才發現，而且找不到理由。

## 這個專案的執行環境

node_modules 是 Windows 版，工具要用 Windows 的 Node 執行；WSL 也連不到 Windows 的 localhost，所以瀏覽器測試要用 Windows 版 Playwright。細節、輔助腳本和常見錯誤見 references/05-implementation.md 的「執行環境」。
